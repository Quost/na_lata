## Problema

Selecionar marca e exibir seus produtos e avaliação geral.

## Entrega de código

Implementar o módulo Flutter `lib/features/brands/brands_feature.dart`. Não basta alterar texto, documentação ou devolver dados fixos. Quem implementa serviço/helper deve demonstrar entrada/resultado/erro no módulo conectado à Oficina.

## Critérios de aceite

- Média ponderada por avaliações, total de avaliações e navegação para produto.
- Estado vazio/erro tratado quando aplicável.
- Teste manual descrito no PR; lógica de parsing, agregação e moderação com teste automatizado.
- `flutter analyze` e `flutter test` passam; PR revisado por um colega.

## Contratos e arquivos

- Pasta principal: `lib/features/brands/`.
- Arquivos adicionais: nenhum obrigatório; testar na própria pasta de testes.
- Usar catálogo local importado. Agregar todas as reviews dos produtos da marca, não tirar média das médias. Sem marca não entra na lista de marcas.
- Ler [contratos](https://github.com/ADSSTech/na_lata/blob/main/docs/CONTRATOS.md).
- Não editar core/registro de rotas nem dependências sem coordenar com o professor.

## Dependências

T10 para helper; fake até T08. Desenvolver com fake/fixture enquanto a dependência não foi integrada. Módulos recebem `FeatureContext`; produto pode ser null na Oficina. Usar a ficha do catálogo para cenários de produto.

## Roteiro de teste

Executar os critérios acima com um exemplo válido e um inválido/vazio. Registrar aparelho, modo demo/Supabase e evidência no PR. Validar integração real quando dependências estiverem disponíveis.

## Fluxo de trabalho

Assuma a issue → branch `feat/NUMERO-descricao` → código → commit → PR com `Closes #NUMERO` → revisão de colega → ajustes → merge coordenado.

Identificador pedagógico: **T13**. Use o número real do GitHub no nome da branch e no PR.

## Padrões compartilhados e testes

Use o [design system](https://github.com/ADSSTech/na_lata/blob/main/docs/DESIGN_SYSTEM.md) e os [clientes padronizados](https://github.com/ADSSTech/na_lata/blob/main/docs/CLIENTES.md). Widgets não chamam Supabase/HTTP diretamente. Teste sucesso, erro/vazio e automatize regras/interações relevantes com fakes. Vocês são livres para propor novas tasks com critérios de aceite e plano de testes.
