## Problema

Editar apelido do usuário e persistir no perfil.

## Entrega de código

Implementar o módulo Flutter `lib/features/nickname/nickname_feature.dart`. Não basta alterar texto, documentação ou devolver dados fixos. Quem implementa serviço/helper deve demonstrar entrada/resultado/erro no módulo conectado à Oficina.

## Critérios de aceite

- Entre 2 e 40 caracteres após trim; feedback de erro/sucesso; comentários usam apelido atualizado.
- Estado vazio/erro tratado quando aplicável.
- Teste manual descrito no PR; lógica de parsing, agregação e moderação com teste automatizado.
- `flutter analyze` e `flutter test` passam; PR revisado por um colega.

## Contratos e arquivos

- Pasta principal: `lib/features/nickname/`.
- Arquivos adicionais: lib/data/supabase_community.dart.
- Editar apenas setNickname; tabela profiles; implementar fake correspondente; não trocar identidade da sessão.
- Ler [contratos](https://github.com/ADSSTech/na_lata/blob/main/docs/CONTRATOS.md).
- Não editar core/registro de rotas nem dependências sem coordenar com o professor.

## Dependências

Nenhuma. Desenvolver com fake/fixture enquanto a dependência não foi integrada. Módulos recebem `FeatureContext`; produto pode ser null na Oficina. Usar a ficha do catálogo para cenários de produto.

## Roteiro de teste

Executar os critérios acima com um exemplo válido e um inválido/vazio. Registrar aparelho, modo demo/Supabase e evidência no PR. Validar integração real quando dependências estiverem disponíveis.

## Fluxo de trabalho

Assuma a issue → branch `feat/NUMERO-descricao` → código → commit → PR com `Closes #NUMERO` → revisão de colega → ajustes → merge coordenado.

Identificador pedagógico: **T23**. Use o número real do GitHub no nome da branch e no PR.

Widgets não chamam Supabase/HTTP diretamente. Teste sucesso, erro/vazio e automatize regras/interações relevantes com fakes.
