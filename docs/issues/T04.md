## Problema

Criar entrada manual para encontrar e importar produto.

## Entrega de código

Implementar o módulo Flutter `lib/features/barcode/barcode_feature.dart`. Não basta alterar texto, documentação ou devolver dados fixos. Quem implementa serviço/helper deve demonstrar entrada/resultado/erro no módulo conectado à Oficina.

## Critérios de aceite

- Aceita 8 a 14 dígitos preservando zeros; mostra loading, ausência e retry; abre ficha ao encontrar.
- Estado vazio/erro tratado quando aplicável.
- Teste manual descrito no PR; lógica de parsing, agregação e moderação com teste automatizado.
- `flutter analyze` e `flutter test` passam; PR revisado por um colega.

## Contratos e arquivos

- Pasta principal: `lib/features/barcode/`.
- Arquivos adicionais: nenhum obrigatório; testar na própria pasta de testes.
- Consultar catálogo primeiro; se ausente, usar OFF e importar. Não enviar códigos demo para OFF. Desabilitar botão enquanto consulta.
- Ler [contratos](https://github.com/ADSSTech/na_lata/blob/main/docs/CONTRATOS.md).
- Não editar core/registro de rotas nem dependências sem coordenar com o professor.

## Dependências

T01/T02 no modo real. Desenvolver com fake/fixture enquanto a dependência não foi integrada. Módulos recebem `FeatureContext`; produto pode ser null na Oficina. Usar a ficha do catálogo para cenários de produto.

## Roteiro de teste

Executar os critérios acima com um exemplo válido e um inválido/vazio. Registrar aparelho, modo demo/Supabase e evidência no PR. Validar integração real quando dependências estiverem disponíveis.

## Fluxo de trabalho

Assuma a issue → branch `feat/NUMERO-descricao` → código → commit → PR com `Closes #NUMERO` → revisão de colega → ajustes → merge coordenado.

Identificador pedagógico: **T04**. Use o número real do GitHub no nome da branch e no PR.
